The `approval-chain` example implements a production-grade human-in-the-loop approval flow using Sapiom's `pauseUntilSignal` primitive. An ordered list of approvers — for example, Legal → Finance → the CEO — must each sign off on a subject (a contract, a budget, a policy change) **in order**. The run presents each gate, suspends at zero cost while idle, sends reminder nudges if the approver goes silent, escalates to a human channel if they never respond, and — if any party rejects — walks a **saga compensation** pattern to notify everyone who already approved that the chain was cancelled. This example is the reference implementation for durable workflows requiring human decisions without polling or burning compute while waiting.

## What this example demonstrates

    `approval.decision` signal. The run survives the wait in durable storage —

  <Card title="Saga compensation" icon="rotate-left">

  <Card title="Reminder and escalation loop" icon="bell">

## Step graph

```text
start → present ─(pause: approval.decision, $0 while idle)─▶ decide
          ▲                                                    │
          │ approve & more gates                              │
          └────────────────────────────────────────────────── ┤
        remind ─(pause: approval.decision)────────────────────┤ reminder tick (budget left)
          ▲                                                     │
          └───────────────────────── reminder tick ─────────────┤
                                                                 │
     reject │              approve & last gate │        timeout / no-response │
            ▼                                  ▼                              ▼
       compensate                          finalize                       escalate
       (terminal)                          (terminal)                      (terminal)
```

| Step | Kind | Role |
|---|---|---|
| `start` | compute | Parse input, initialise chain state in `ctx.shared` |
| `present` | pause | Email the current approver, then `pauseUntilSignal` |
| `decide` | compute | Route the resume payload to the next gate, reminder, finalize, compensate, or escalate |
| `remind` | pause | Email a reminder, then re-pause on the same gate |
| `finalize` | compute (terminal) | The single irreversible action, reached only when every party approved |
| `compensate` | compute (terminal) | Saga rollback — notify prior approvers the chain was cancelled |
| `escalate` | compute (terminal) | Alert the escalation channel when a gate goes silent |

## Core patterns

### pauseUntilSignal — durable suspension at $0

The heart of the approval chain is `pauseUntilSignal`. When `present` runs, it emails the current approver and then immediately suspends:

```typescript
import { pauseUntilSignal } from "@sapiom/agent";

const APPROVAL_SIGNAL = "approval.decision";

const present = defineStep({
  name: "present",
  next: [],
  pause: { signal: APPROVAL_SIGNAL, resumeStep: "decide" },
  async run(_input, ctx) {
    // ... email the current approver ...

    return pauseUntilSignal({
      signal: APPROVAL_SIGNAL,
      resumeStep: "decide",
      correlationId: ctx.executionId,
    });
  },
});
```

The run is now dormant — no compute, no cost. It resumes only when something fires the `approval.decision` signal with the run's `executionId` as the `correlationId`. The resume payload becomes the `decide` step's `input`.

<Warning>
  The gates in this example carry **no `timeoutMs`** on purpose. The engine's
  paused-run reaper *terminates* a run when its pause deadline lapses — it does not
  resume the step. Adding a `timeoutMs` here would silently kill any approval that
  takes longer than the deadline, bypassing the graceful `escalate` step entirely.
  Reminders and escalation are driven by the signal convention, not by a deadline.
</Warning>

### The decision router (`decide`)

`decide` is the resume target. Its `input` is the approval payload the approver fires:

```typescript
const decide = defineStep({
  name: "decide",
  next: ["present", "remind", "finalize", "compensate", "escalate"],
  async run(payload: ApprovalDecision, ctx) {
    const decision = payload?.decision;

    if (decision === "approve") {
      // advance to the next gate, or finalize on the last one
      const nextIndex = gateIndex + 1;
      if (nextIndex < approvers.length) {
        ctx.shared.set("gateIndex", nextIndex);
        return goto("present", {});
      }
      return goto("finalize", {});
    }

    if (decision === "reject") {
      return goto("compensate", { rejectedBy: current?.id, notes: payload?.notes });
    }

    if (decision === "timeout") {
      return goto("escalate", { reason: "timeout" });
    }

    // No explicit decision → reminder tick
    const reminders = (ctx.shared.get("reminders") ?? 0) + 1;
    ctx.shared.set("reminders", reminders);
    if (reminders > maxReminders) {
      return goto("escalate", { reason: "no-response" });
    }
    return goto("remind", {});
  },
});
```

The signal payload drives the routing:

| Payload | Branch |
|---|---|
| `{ "decision": "approve" }` | Advance to the next gate, or `finalize` on the last |
| `{ "decision": "reject" }` | Walk `compensate` — saga rollback |
| `{ "decision": "timeout" }` | Walk `escalate` immediately |
| `{ "decision": "remind" }` or empty | Reminder tick — `remind` while budget lasts, then `escalate` |

### Saga compensation (`compensate`)

When any approver rejects, `compensate` notifies everyone who already signed off that the chain was cancelled. This is the saga pattern: if the irreversible action only happens at `finalize` (reached only after **every** party approved), then a rejection at gate 3 of 5 means gates 1 and 2 approved on the assumption the chain would complete. The `compensate` step unwinds that assumption:

```typescript
const compensate = defineStep({
  name: "compensate",
  next: [],
  terminal: true,
  async run(input, ctx) {
    const approvals = ctx.shared.get("approvals") ?? [];
    const approvers = ctx.shared.get("approvers") ?? [];

    // Notify everyone who already approved
    for (const approved of approvals) {
      const contact = approvers.find((a) => a.id === approved.id)?.email;
      await notify(ctx, contact, `Cancelled: ${subject}`, /* ... */);
    }

    return terminate({
      committed: false,
      outcome: "rejected",
      subject,
      rejectedBy: input.rejectedBy,
      approved: approvals,
      compensated,
    });
  },
});
```

### Chain state in `ctx.shared`

All mutable chain state — current gate index, recorded approvals, the transition trail — lives in `ctx.shared`. Shared state is durable: it persists across `pauseUntilSignal` suspensions and is accessible in every subsequent step via `ctx.shared.get(key)` and `ctx.shared.set(key, value)`.

```typescript
interface Shared extends Record<string, unknown> {
  subject: string;
  approvers: Approver[];
  gateIndex: number;
  reminders: number;
  approvals: RecordedApproval[];
  trail: Transition[];
  escalateTo: string | null;
  ledgerHandle: string | null;
  maxReminders: number;
  dryRun: boolean;
}
```

### Optional Postgres audit ledger

Pass a `ledgerHandle` to persist every state transition to a durable `approval_chain_ledger` Postgres table via `ctx.sapiom.database`. The ledger is best-effort — the chain never fails if the database is unreachable:

```typescript
async function recordTransition(ctx, phase, note) {
  // Always write to ctx.shared (survives pauses)
  const trail = ctx.shared.get("trail") ?? [];
  ctx.shared.set("trail", [...trail, transition]);

  // Best-effort: also write to the durable Postgres ledger
  const handle = ctx.shared.get("ledgerHandle");
  if (!handle) return;  // no ledger configured — fine
  await persistTransition(ctx, handle, transition).catch((err) => {
    ctx.logger.warn("ledger: persist failed (kept in shared)", { error: err.message });
    // Never throws — the ledger failure must not stop the chain
  });
}
```

## Running the example

<Steps>
  <Step title="Install dependencies">
    ```bash
    cd examples/approval-chain
    npm install
    ```
  </Step>

  <Step title="Set up environment">
    ```bash
    cp ../.env.example .env
    # Edit .env and set SAPIOM_API_KEY
    ```
  </Step>

  <Step title="Trace locally (free, capabilities stubbed)">
    With the MCP, run `sapiom_dev_agents_run_local`. Capabilities are stubbed and
    pauses are auto-resumed with an empty payload — so the default offline trace
    walks `present → reminder(s) → escalate` for free, with no Postgres touched.

    <Note>
      Keep `maxReminders` small (default is `2`) so the offline trace terminates
      quickly. Each empty auto-resume fires a reminder tick.
    </Note>
  </Step>

  <Step title="Deploy and run a live approval">
    ```bash
    npx @sapiom/cli agents deploy
    npx @sapiom/cli agents run --input '{
      "subject": "Master Services Agreement v3",
      "approvers": [
        { "id": "legal", "name": "Legal", "email": "legal@example.com" },
        { "id": "finance", "name": "Finance", "email": "finance@example.com" }
      ],
      "escalateTo": "ops@example.com",
      "maxReminders": 2
    }'
    ```

    The run pauses at the first gate. The `legal` approver receives an email with
    instructions.
  </Step>

  <Step title="Fire the approval signal">
    Resume the paused run by firing the `approval.decision` signal via the MCP tool
    `sapiom_dev_agents_signal` (or `workflow_signal`). Use the paused run's
    `executionId` as the `correlationId`:

    ```json
    {
      "signal": "approval.decision",
      "correlationId": "<executionId of the paused run>",
      "payload": { "decision": "approve" }
    }
    ```

    Fire one `approve` per approver to reach `finalize`. To exercise other branches:

    | Payload | Branch reached |
    |---|---|
    | `{ "decision": "approve" }` | Next gate, or `finalize` on the last |
    | `{ "decision": "reject" }` | `compensate` — notifies prior approvers |
    | `{ "decision": "remind" }` | Re-notifies, re-pauses |
    | `{ "decision": "timeout" }` | `escalate` immediately |
  </Step>
</Steps>

## Adapting this example

<Accordion title="Enable the durable Postgres audit ledger">
  Pass `ledgerHandle` in the run input (or set `config.LEDGER_HANDLE`). The first
  run with this handle creates the `approval_chain_ledger` table and begins appending
  transitions:

  ```json
  {
    "ledgerHandle": "my-approval-ledger",
    "subject": "Q4 budget",
    "approvers": [{ "id": "cfo", "name": "CFO", "email": "cfo@example.com" }]
  }
  ```

  The table schema is:
  ```sql
  (execution_id, seq) PRIMARY KEY
  subject, gate_index, approver_id, phase, note, recorded_at
  ```
</Accordion>

<Accordion title="Replace the finalize action">
  The `finalize` step is intentionally a notification stub. Replace the body
  with the action the sign-off authorises — countersigning a contract, disbursing
  a budget, publishing a policy. The `dryRun` flag suppresses it during testing:

  ```typescript
  if (dryRun) {
    return terminate({ committed: false, dryRun: true, outcome: "dry-run" });
  }
  // Replace this with the real irreversible action
  await disburseBudget(subject, approvals);
  return terminate({ committed: true, outcome: "completed" });
  ```
</Accordion>

<Accordion title="Wire a cron for automatic reminders">
  To send timed reminders, set up a scheduled agent or a cron webhook that fires
  `{ "decision": "remind" }` on a cadence, and eventually `{ "decision": "timeout" }`
  after a deadline. The `maxReminders` field controls how many reminder ticks a gate
  accepts before it escalates automatically.
</Accordion>
