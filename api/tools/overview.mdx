The `@sapiom/tools` package is the programmable surface of the Sapiom platform. It exposes the exact same capabilities your agents invoke over MCP — sandboxes, repositories, managed model runs, file storage, email, memory, and more — as typed TypeScript namespaces you can call directly from your own code, from within an agent step, or from any Node.js script. This page covers installation, the two authentication modes, all available capability namespaces, subpath imports, usage analytics, and the `client.shutdown()` lifecycle method.

## Installation

```bash
npm install @sapiom/tools
# or
pnpm add @sapiom/tools
```

## Authentication modes

There are two ways to authenticate. Both expose an identical capability surface — choose the one that fits your usage context.

<Tabs>
  <Tab title="Explicit (standalone)">
    Pass an API key to `createClient`. This is the right choice for standalone scripts, CI jobs, and any code running outside a Sapiom agent step.

    ```typescript
    import { createClient } from "@sapiom/tools";

    const sapiom = createClient({ apiKey: process.env.SAPIOM_API_KEY });
    await sapiom.sandboxes.create({ name: "demo" });
    ```
  </Tab>
  <Tab title="Ambient (inside an agent step)">
    Import capability namespaces directly from `@sapiom/tools`. Inside a Sapiom agent step the runtime injects credentials automatically; outside a step the package falls back to `SAPIOM_API_KEY` from the environment.

    ```typescript
    import { sandboxes, repositories, models } from "@sapiom/tools";

    await sandboxes.create({ name: "demo" });
    ```
  </Tab>
</Tabs>

## Quickstart

```typescript
import { createClient } from "@sapiom/tools";

const sapiom = createClient({ apiKey: process.env.SAPIOM_API_KEY });

// Create a repo, have a coding agent build into it, then publish.
const repo = await sapiom.repositories.create("landing-page");
const run = await sapiom.models.coding.run({
  task: "Build a one-page marketing site in index.html.",
  gitRepository: repo,
});

if (run.result?.success) {
  const { sha } = await repo.pushFromSandbox(run.sandbox, {
    message: "build: landing",
  });
  console.log("published", sha);
}
```

## Subpath imports

Every namespace is tree-shakable via its own subpath. Import from the subpath when you want to load only one capability:

```typescript
import { sandboxes } from "@sapiom/tools/sandboxes";
import { repositories } from "@sapiom/tools/repositories";
import { models } from "@sapiom/tools/models";
```

The subpath and barrel re-exports are identical in behaviour; the subpath just avoids bundling the entire package when you only need one capability.

## Composing capabilities

Capabilities are designed to work together. The most common composition is a coding run followed by a repository push — the coding agent writes the files, and your code commits and publishes them deterministically:

```typescript
import { repositories, models } from "@sapiom/tools";

const repo = await repositories.create("api");
const run = await models.coding.run({
  task: "Add a /health endpoint that returns 200 OK.",
  gitRepository: repo,
});
if (run.result?.success) {
  await repo.pushFromSandbox(run.sandbox, { message: "feat: health" });
}
```

Another built-in composition: pass `storage` to `contentGeneration.images.create` and each generated image is persisted to `fileStorage` inline — no extra round-trip needed:

```typescript
const out = await contentGeneration.images.create({
  prompt: "a logo",
  storage: { visibility: "private" },
});
const { downloadUrl } = await fileStorage.getDownloadUrl(out.images![0].fileId!);
```

## Usage analytics

The SDK can emit anonymous, per-capability analytics events (one `capability.call` event per request). Each event carries the capability name, the request URL path (query strings are stripped), HTTP status, duration, and request size — never request or response bodies. Analytics describe calls to Sapiom's own API only; nothing is captured about third-party traffic.

By default nothing is sent anywhere. Opt out at any time:

```bash
SAPIOM_TELEMETRY_DISABLED=1
# or
DO_NOT_TRACK=1
```

<Note>
  Delivery is batched in the background and can never throw, block, or slow a capability call. One-shot scripts do not need to call `shutdown()` — buffered events flush automatically on process exit.
</Note>

## client.shutdown()

If your process constructs many clients over its lifetime (one per execution, for example), call `client.shutdown()` when you are done with each one. It flushes any buffered analytics events and detaches the emitter's process exit hook.

```typescript
const sapiom = createClient({ apiKey: process.env.SAPIOM_API_KEY });
try {
  await sapiom.sandboxes.create({ name: "job" });
  // ... do work
} finally {
  await sapiom.shutdown();
}
```

`shutdown()` is idempotent, never rejects, and resolves immediately when there is nothing to release. It covers every client derived from the same root via `withAttribution(...)`. Capability calls made after shutdown still work; they just no longer emit analytics.
